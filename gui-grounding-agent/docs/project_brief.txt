2. Project summary

I’m building a local, open-weight, VLM-powered agent that takes a screenshot and a natural-language instruction (e.g. “click the Downloads folder”), localizes the target UI element as a bounding box or point, and executes the click. The research task is called GUI grounding. Related work includes ScreenSpot, SeeClick, UGround, OS-Atlas, ShowUI and CogAgent. The project is a scoped-down version of the idea behind products like HeyClicky, focused on the computer-vision core (grounding) rather than a full autonomous agent.

3. Research gap and hypotheses

Does combining classical computer-vision preprocessing (edge and contour-based candidate region proposals) with a fine-tuned small VLM improve GUI grounding accuracy and robustness, especially on small UI elements, compared to the fine-tuned VLM alone? And does the result hold on out-of-distribution, adversarially styled UI elements (CAPTCHA-style checkboxes) the model never trained on?

H1 (ablation): classical preprocessing aid improves grounding accuracy, particularly for small elements.
H2 (generalization): a model fine-tuned on standard app and web UI transfers imperfectly to adversarial or stylized UI.

5. Technical approach
Model: Florence-2-base (~0.23B parameters), which supports grounding natively. Backup options are Qwen2-VL-2B (stronger zero-shot grounding) and Moondream2 (easiest to run).
Training method: QLoRA (4-bit quantization with LoRA adapters) using transformers, peft, bitsandbytes and accelerate.
Why supervised fine-tuning, not RL: every example has an exact ground-truth box, so a direct loss (cross-entropy on location tokens, with IoU or L1 as evaluation and diagnostics) is simpler, more stable and more sample-efficient.
Classical preprocessing aid: Canny/Sobel edges, then contour extraction, then candidate UI-element boxes. These feed the VLM as crop hints or overlays, or are used to snap and re-rank its predictions. The exact integration method is a design decision to settle in Week 3 and justify in the report.
Optional agentic layer: a perceive, reason, act, observe loop where the model proposes the next action from a small allowed set. This is inference-time prompting, not a trained policy. Fixed scripted sequences are the fallback if it proves unreliable.
6. Pipeline (for the architecture diagram)

Screenshot capture (mss) → classical preprocessing (edges, contours, candidate regions) → VLM grounding inference (instruction + image → box or point) → post-processing (map coordinates back to real screen resolution, NMS if needed) → action execution (pyautogui, Bézier movement) → verification (re-screenshot and diff for success or failure logging).

7. Data
Public base: a ScreenSpot subset (web, mobile and desktop screenshots with instruction, element and bounding-box triples).
Self-collected: 150-300 screenshots covering file explorer, browser (including the two sites used in the demo), and settings menus. Each has several instruction-box annotations, made with labelImg or a small OpenCV click-to-box script (which I can document as a preprocessing utility).
OOD test set: self-built HTML pages with CAPTCHA-style checkboxes. These are never used in training.
Splits: train, val and test, with the split rationale documented. Preprocessing covers resizing and normalization, coordinate scaling, instruction formatting into the model’s input format, and optional tiling for small elements.
8. Demo task

A fixed, scripted sequence where the VLM grounds each step:

File navigation: open a folder, find a file, open it.
Browser task: go between two websites, copy a list of links from site A, paste them into site B, and click download. (Text extraction here is OCR or DOM-free text copy, a separate technique from grounding, and the report will say so.)
Checkbox test page: locate and click the checkbox.
9. Experiments and metrics
Click accuracy (prediction falls inside the ground-truth box), the standard ScreenSpot metric, so I can compare to published numbers.
IoU against ground-truth boxes.
Zero-shot vs fine-tuned comparison (the main chart).
Ablations: with and without classical preprocessing, image resolution, tiling for small elements.
Per-category breakdown: buttons, text fields, icons, menus. Small elements are expected to be hardest.
OOD test: checkbox-page accuracy for zero-shot vs fine-tuned.
Inference latency on the 8GB GPU, plus honest failure analysis.
